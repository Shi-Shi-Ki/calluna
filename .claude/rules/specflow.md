# specflow: 仕様書駆動のテスト合意フロー

<!-- calluna（specflow）で管理。CLAUDE.md・REVIEW.md・team-*.md は cosmos の管轄なので、ここに書かない -->

人は「何が正しいか（仕様と例）」を決め、最終判断をする。AIは生成し、CIが機械的に検証する。
テストは「人とAIの合意を、実行できる形で残したもの」。自動化そのものは目的にしない。

## フェーズ
1. 仕様: GitHub Issue（テンプレート「仕様書」）。業務ルールには番号がある。
2. ケース表（`/cases`）: `specs/<Issue番号>-<slug>/cases.yaml` とテスト、実装のスタブを作る。`cases.md` は生成物。
3. 承認: 人が PR の `cases.md` を読み、ラベル `cases:approved` を付ける。この時点のコミットが「合意」。
4. 実装（`/implement`）: テストを通す実装を書く。**`specs/` と `tests/` は変更しない。**
5. CI・レビュー・人の受け入れ確認（`cases.md` の「人が確認する項目」）。コードレビューは cosmos の `@claude review` で行い、specflow は行わない。

## ケース表のルール（フェーズ2）
- ID は `TC<Issue番号>-<2桁>`。決定事項は `D<Issue番号>-<n>`、仮定は `A<Issue番号>-<n>`、人の確認項目は `M<Issue番号>-<2桁>`。
- 1ケース = 1テスト。テスト名は `<ID> <日本語の文>`（例: `TC1-02 期限当日の申請は督促しない`）。
- テストは `cases.yaml` を読み込んで `test.each` などで回す。期待値をテストコードに二重に書かない。
- 仕様の例の表は、すべてケースに含める。`spec_ref` に「ルール2」「例1」「決定D1-1」「仮定A1-1」のように根拠を書く。
- `given` / `then`（人が読む文）と `input` / `expected`（テストが比べる値）は同じことを言うこと。並び順・件数・値を1件ずつ突き合わせる。`cases.md` には両方が並んで表示される。
- `cases.yaml` の文字列に `#` や `: ` を含むときは `"…"` で囲む。行末コメントは使わない（値が黙って切れるため、検査で止まる）。
- 観点チェックリスト: 正常 / 空の値 / 重複 / 境界値 / 異常値 / シートの破損 / 権限 / 同時実行。
  リスク「低」は正常系と構造の破損だけ。「中」は全観点を検討。「高」は全観点に加えて、データを書き換える操作の前後を確認する。
- 外部（SpreadsheetApp、カレンダー、HTTPなど）は単体テストではすべて偽物にする。
- テストを書かないもの: 使い捨てのツール、シートを読み書きするだけの部分。カバレッジの数値は目標にしない。

## 境界値の作り方
- 仕様に出てくる「比較」と「区切り」をすべて境界として洗い出し、`cases.yaml` の `boundaries` に書く。
  人はこの一覧で「境界の見落とし」を確認する。
- 各境界は「すぐ内側・ちょうど・すぐ外側」の3点をケースにする。片側だけは不可。

| 種類 | 確認する値 | 例 |
| --- | --- | --- |
| 日付の比較 | 前日 / 当日 / 翌日。セルに時刻が入っている場合（当日 23:59 など）も1点 | 退職日と基準日、期限と基準日 |
| 数量・件数 | 0 / 1 / 2以上。上限があれば 上限-1 / 上限 / 上限+1 | 在籍0人の部署、1行だけのシート |
| 並び順 | 同じ値が並ぶとき（同数・同日）、入力がすでに逆順のとき | 人数が同じ部署 |
| 文字列 | 空文字 / 空白だけ / 前後の空白 / 全角と半角 | 「総務部 」と「総務部」 |
| グループ化 | 1グループだけ / 全員が対象外になるグループ | 全員退職した部署 |

## ブロッカーと仮定の線引き
- **ブロッカー**（ケース表を作らずに質問だけ返す。最大5個、選択肢付き、1往復で答えられる形）:
  - 業務上の判断で期待結果が変わるもの。特に、境界ちょうどの扱い（当日を含むか）、同値のときの順序、
    空欄・未設定のデータの扱い（除外する / エラーで止める / 別枠で数える）、集計や処理の対象に含めるかどうか。
  - データの削除・上書き・外部への送信の範囲。
  - AIが「承認前に人が確認すべき」と考えたもの。`manual_checks` に回して先に進めてはいけない。
- **仮定**（AIが選んで `assumptions` に書き、関係するケースの `spec_ref` から参照する）:
  - 業務上の答えが変わらない技術的な選択だけ。例: すべて空の行は無視する、構造が壊れていたら何も書かずに止める、
    日付はスクリプトのタイムゾーンで判定する、出力の見出し行。
- **決定事項**（`decisions`）: Issue 本文やコメントで回答済みの点。仕様として扱い、ブロッカーにも仮定にもしない。`source` に「回答B1」のように出どころを書く。
- 迷ったらブロッカーにする。`manual_checks` の `when` に「承認前」は書かない（検査で止まる）。

## コードのルール
- GAS: 入出力（`getDataRange().getValues()` / `setValues()`）は薄いアダプターに閉じ込め、判断は純粋関数に置く。
- 列は位置でなくヘッダー名で特定する。構造が合わなければ何も書かずに止める。
- clasp 2.x の TS（ts2gas）では `import` / `export` を使わない。Node から読むために末尾で `if (typeof module !== 'undefined') module.exports = {...}` を使う。

## 実装フェーズでの禁止事項
- `specs/`、`tests/` を変更しない（hook と CI で止まる）。CI 上では `.claude/`、`.github/`、`CLAUDE.md` も変更しない。
- テストが仕様と矛盾していると考えたら、変更せずに最終報告に「ケース表への指摘」として書く。人が仕様変更として判断する。
